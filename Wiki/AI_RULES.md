# Правила для нейросетей

Это действующие правила работы с Mad Slime. Читай этот файл перед каждым ответом. Устройство игры описано в [атласе систем](<Атлас систем.md>).

## Общение и границы задачи

- Общайся по-русски, коротко и прямо. Объясняй простыми словами, без лишних англицизмов, похвалы и вступлений.
- Пользователь — опытный программист Unity. Объясняй код, только если об этом попросили.
- Выполняй именно запрошенную работу. Не добавляй улучшения «на будущее», новые зависимости и лишние изменения.
- Если просят разобраться или обсудить решение, сначала анализируй. Не меняй код без запроса на изменение.
- Не соглашайся автоматически: укажи на проблему и предложи более простое решение, если оно есть.
- Для нетривиальной задачи дай короткий план и двигайся по нему.
- Если важное условие неизвестно, задай конкретный вопрос с вариантами. Если пользователь пропустил вопрос, не считай это ответом или согласием.
- Перед созданием системы найди существующую реализацию. Не создавай дубликаты; при неоднозначности уточни, какую часть нужно изменить.
- Сначала смотри соседний код, зависимости и места вызова. Не переписывай класс целиком без причины.
- Не придумывай Unity API. Если не уверен, проверь официальную документацию для версии проекта.
- Код, имена, исключения, сообщения анализаторов и прочие сообщения разработчику пиши на английском.
- Не создавай средства проверки, настройки и другие инструменты без прямой просьбы «напиши инструмент».
- Не создавай дополнительные README, отчёты, планы и журналы работы без просьбы. Для уже запрошенного длительного журнала используй один файл без лишних записей.
- При разборе системы указывай её ответственность, входные данные, результат, зависимости и время жизни.
- Не заявляй, что проверка прошла, если её не запускал. В завершении укажи результат и существенные ограничения проверки.

## Основа проекта

- Проект использует Unity 2022.3 LTS и трёхмерную физику. По умолчанию нужен `Collider`, а не `Collider2D`.
- Код игры находится в `Assets/MadSlime/Scripts/`. Одна система — одна папка.
- Внутри системы: `Data` — данные и настройки, `Logic` — поведение, `View` — отображение. Дополнительные папки: `Interfaces`, `Adapters`, `Editor`.
- Весь интерфейс находится в `UI`, внутри — разделы по системам. Сборка зависимостей находится в `DI`.
- Пространство имён повторяет папку: например, `MadSlime.Player.Logic`.
- Сборки: `MadSlime.Core` — общие данные и интерфейсы, `MadSlime.Gameplay` — игровая логика, `MadSlime.UI` — интерфейс. Проверяй направление ссылок между ними.
- При переносе файла сохраняй его `.meta` и GUID. Проверяй, к какой сборке его относит `.asmref`.
- Не меняй пути в `Resources` без проверки всех загрузок по строковому пути.
- Новую механику подключай к существующей подготовке и запуску своей сцены. Текущая цепочка: `SceneState.Start` → `SceneStateMachine` → `GameStartup` и подготовка сцены → запуск её машины состояний.
- Пользуйся существующими средствами передачи зависимостей VContainer. Для компонентов принят `[Inject] Construct(...)`, для обычных служб — конструктор.

## Архитектура

- Один класс отвечает за одну понятную задачу. Не объединяй разные обязанности и не дроби одну обязанность на множество пустых классов.
- Предпочитай сочетание небольших объектов глубокому наследованию. Наследник сохраняет смысл и поведение контракта родителя.
- Храни данные отдельно от активного поведения. У каждого изменяемого значения должен быть понятный владелец.
- Передавай зависимости явно. Не ищи службы через `GameObject.Find`, `Transform.Find`, `FindObjectOfType` и похожие поиски по сцене.
- Не вводи общий поиск служб, глобальный посредник событий, ECS или новый способ внедрения зависимостей без реальной необходимости.
- Не создавай одиночку без прямой просьбы. Это не отменяет строгий запрет статики ниже.
- Интерфейс нужен для существующей задачи. Запрещены и один огромный интерфейс «на всё», и множество мелких интерфейсов, которые всегда используются вместе.
- Не создавай лишние уровни абстракции, фабрики фабрик и возможности «на потом».
- При нескольких последовательных состояниях используй явную машину состояний. Не заменяй её набором несогласованных флагов. Для двух простых состояний допустим один `bool`.
- Создание и настройку объектов из префабов выполняй в фабрике или существующем средстве создания. Не разбрасывай `Instantiate` по игровой логике.
- Убирай повторяющийся и действительно неиспользуемый код. Учитывай вызовы Unity, реализации интерфейсов и ссылки в сценах и префабах.
- Свойства и проверки доступности не меняют состояние. Очистка данных, покупка и сохранение выполняются отдельными действиями.
- Изменения между системами делай только по необходимости задачи; связывай системы явными зависимостями и событиями.

## Строгий запрет статики — П-61

Запрещены статические классы, поля, включая `static readonly`, конструкторы, методы, свойства и события. Правило действует для игрового кода и средств редактора независимо от доступности.

Единственное исключение — утилиты без состояния, подобные `ArgumentGuard`: статический класс и его методы могут работать только с переданными аргументами. Статические поля и конструкторы запрещены и в таких утилитах.

Оптимизация, удобство, кэширование и требования редакторского API не дают исключений. Игровые службы нельзя объявлять утилитами ради обхода запрета. Этот пункт имеет приоритет над прежними примерами и правилами именования статики. `const` разрешён.

## Имена и расположение кода

| Что | Правило |
| --- | --- |
| Классы, структуры, перечисления, свойства и методы | `PascalCase` |
| Интерфейсы | `I` и понятное имя, например `ISkinStorage` |
| Закрытые и внутренние поля | `_camelCase`, в том числе `readonly` и `[SerializeField]` |
| Остальные поля, константы | `PascalCase` |
| Параметры и локальные переменные | `camelCase` |
| Логические поля и свойства | Понятная проверка: `_isRunning`, `IsReady` |
| Обработчики событий | Именованный метод с префиксом `On` |
| События | `PascalCase`, название передаёт действие или результат, например `Moving`, `Collected` |

- Явно указывай доступность членов и типов.
- Название метода начинается с глагола и объясняет действие. Не повторяй имя класса в названиях его полей и методов.
- Метод `Try*` возвращает `bool`.
- Не используй безликие имена и лишние сокращения. `i` и `j` разрешены только как счётчики простых циклов. Вместо одиночных `x`, `z`, `t` используй, например, `offsetX`, `offsetZ`, `progress`.
- Не создавай классы с расплывчатыми именами `Manager`, `Handler`, `Utility`, `Helper`. Название должно объяснять конкретную обязанность.
- Предпочитай явные типы. `var` допустим, когда тип очевиден, но редактор помечает его мягкой подсказкой.
- Имя файла совпадает с основным типом. Для частей класса допустим `ClassName.Part.cs`.
- Один файл — один класс. Существующее исключение проекта: сериализуемые описания строк настройки могут находиться рядом с владеющим ими `ScriptableObject`.
- Не переименовывай поля внешних ответов JSON ради стиля: их имена должны совпадать с ключами платформы. Это относится, например, к `LeaderboardResponse` и `LeaderboardPlayerResponse`.
- Не переименовывай ключи существующих сохранений без отдельной миграции. Имена, связанные с внешним форматом данных, важнее общего правила именования.
- Не исправляй вручную стиль автоматически созданного кода, например `PlayerInputActions.cs`: меняй источник генерации, если это требуется задачей.

## Форматирование

- Базовый стиль — соглашения Microsoft C# с уточнениями этого файла и `.editorconfig`.
- Максимальная длина строки — 120 символов.
- Открывающая фигурная скобка всегда на новой строке. Тела методов, условий и циклов — многострочные; скобки обязательны.
- Не пиши однострочные методы и блоки. Краткие свойства и автосвойства разрешены.
- Смысловые блоки разделяй одной пустой строкой. Не оставляй пустые строки сразу после `{` и перед `}`, не ставь несколько пустых строк подряд.
- Отделяй объявления от действий, условия и циклы — от соседнего кода. `if/else` остаётся одним блоком. Разные секции `case` отделяй пустой строкой.
- Поля одной группы и краткие свойства могут идти подряд. Многострочное свойство отделяется с обеих сторон.
- Порядок членов: `readonly` и `const` поля → поля с атрибутами → остальные поля → делегаты → конструкторы → события → свойства → методы Unity → остальные методы → обработчики событий. Разрешённая статика утилит следует общим правилам порядка членов.
- Внутри группы порядок доступности: `public`, `internal`, `protected internal`, `protected`, `private protected`, `private`. Методы Unity могут стоять перед публичной логикой независимо от доступности.
- Сохраняй относительный порядок `[SerializeField]`: от него зависит порядок настроек в инспекторе. Не переставляй их автоматической очисткой кода.
- Подсказки SA1201–SA1204 не требуют механической перестановки членов. MS0018 проверяет границы блоков, SA1516 в проекте отключён.
- Удаляй неиспользуемые `using`. Не добавляй комментарии в код.

## Условия, свойства и расчёты

- Вместо отрицания `!value` используй `value == false`, в том числе для `TryGetComponent`. Сравнения `bool?` с `true` и `false` разрешены.
- Тернарный оператор, `??` и `??=` запрещены. Используй явный `if/else`.
- Вызов события через `?.Invoke()` разрешён.
- Предпочитай ранний выход лишней вложенности. Для трёх и более ветвей по одному значению используй `switch`.
- По циклу должно быть видно условие завершения. Для длительной работы нужны отмена или понятный выход.
- Вместо явного тела `get` или `set` в реализации класса используй автосвойство либо свойство `=>` над полем. Проверку и изменение состояния с условиями оформляй именованным методом.
- Свойства не выполняют расчёты, поиск, проверку данных и изменение состояния. Простая передача значения из другого поля или свойства допустима.
- Выноси числа с неочевидным смыслом в именованные константы или настройки.
- Сначала вычисляй значения, затем составляй текст. Не выполняй расчёты внутри подстановки строк.
- Применяй `ref` и `out` по назначению, а не для скрытого изменения чужого состояния.
- Не используй LINQ, если он создаёт лишние выделения памяти или ухудшает читаемость. В покадровом коде LINQ запрещён.
- Reflection запрещён.

## События и время жизни

- Используй события C# с `event Action` или `event Action<T>`. `UnityEvent` запрещён. Для других передаваемых функций используй стандартные `Action`, `Func`, `Predicate`.
- Подписывайся именованными обработчиками. Анонимные лямбды при `+=` запрещены.
- Каждой подписке соответствует отписка: `OnEnable`/`OnDisable`, `Awake` или `Start`/`OnDestroy`, либо явное завершение службы.
- Отмена и завершение должны освобождать подписки, запросы паузы и выполняющуюся работу.
- При переопределении методов Unity учитывай логику базового класса и вызывай `base`, если он выполняет необходимую часть работы.

## Проверка входных данных

- Проверяй обязательные зависимости и допустимость параметров до использования. Для этого есть `ArgumentGuard`.
- Для ошибок настройки используй исключение с понятным контекстом. Не скрывай сломанную обязательную зависимость молчаливой заменой или ранним выходом.
- Проверяй диапазоны, положительность и порядок границ. Ограничение значения допустимо там, где это игровое правило, а не способ скрыть ошибочные входные данные.
- Для компонента на том же объекте предпочитай `TryGetComponent` сочетанию `GetComponent` и проверки на `null`.
- Для жёсткой зависимости от компонента на том же объекте применяй `[RequireComponent]`.
- Потенциальное обращение к отсутствующему объекту считается ошибкой. Учитывай порядок подготовки и вызовы до `Awake`.
- В игровом коде не используй `Debug.Log`, `LogWarning`, `LogError` и `Assert` вместо обработки ошибки. При строгом ревью фиксируй все такие вызовы, в том числе в средствах редактора.

## Unity, ожидания и производительность

- Используй TextMeshPro. `ScriptableObject` применяй для оправданных настроек и данных.
- `[SerializeField]` нужен для настройки в редакторе; не открывай поля публично без необходимости.
- Не добавляй лишние `Update` и выделения памяти на каждом кадре. Учитывай работу на мобильных устройствах.
- Для поиска соседних объектов предпочитай `OverlapSphereNonAlloc` и повторно используемый буфер.
- Для асинхронной работы предпочтителен UniTask. Длительную работу связывай с `CancellationToken` владельца; для компонента доступен `GetCancellationTokenOnDestroy()`.
- Явно обрабатывай `OperationCanceledException`. При отмене не продолжай действия завершённой операции.
- Для намеренного запуска без ожидания используй `.Forget()`; методы такого назначения могут возвращать `UniTaskVoid`.
- Ожидание следующего кадра оформляй через UniTask. Если нужна корутина, повторно используй подходящий объект ожидания в поле экземпляра, не создавай его каждый кадр и не вводи статический кэш.

## Интерфейс, текст и управление

- Пользовательские строки хранятся в таблице перевода с заполненными русским, английским и турецким вариантами. Используй `LocalizedText` или `Localization.Get`.
- Не размещай надписи внутри картинок кнопок. Для значков используй изображения без букв.
- Проверяй длину текста на трёх языках, особенно турецком. Кнопки и подписи не должны обрезаться.
- Новые Canvas используют `Scale With Screen Size`. Ориентиры: 1080×1920 и 1920×1080, `match` 0.5. Существующие затронутые Canvas приводи к этому способу масштабирования.
- Показатели игры привязывай к краям и безопасной области экрана. Не задавай расположение фиксированным смещением от центра.
- Проверяй портретное и альбомное расположение, отсутствие перекрытий и доступность кнопок. Сенсорная область кнопки — примерно от 100 пикселей в опорном разрешении.
- Сенсорные элементы показывай при наличии сенсорного ввода. Не показывай подсказки чужой платформы.
- Управление должно переживать смену размера и ориентации окна. Сбрасывай перетаскивание при отключении компонента.
- Игрок остаётся в пределах пола через `Clamper`; не создавай невидимые стены вне устройства уровня.

## Сохранения и связь с платформой

- Постоянные данные меняй через существующие хранилища поверх `SavesCore`. Запись платформе передаёт `Yg2SavesAccess`.
- Новые поля добавляй в `PlayerSaveData`, соответствующее хранилище и его интерфейс, если это требуется. Сохраняй совместимость ключей и проверяй загрузку старых данных.
- Связанные изменения, например списание денег и выдачу покупки, объединяй через `SavesTransaction`. Для важных наград учитывай `ISaveConfirmation` и возможность повторного подтверждения без повторной выдачи.
- Авторизацию запрашивай по действию пользователя или в предусмотренном месте после обучения, а не автоматически при старте.
- При ошибке таблицы рекордов показывай перевод `leaderboard_error` и возможность повтора. Не оставляй бесконечную загрузку.
- Не придумывай имя анонимного игрока: используй ответ и перевод плагина.
- Полноэкранную межуровневую рекламу показывай на стыке уровней с ограничением частоты, а не в середине захода или на старте.
- На кнопке рекламной награды нужен значок видео без запечённой надписи.
- Не удаляй проверки `IAdsService.IsPauseGame` и `YG2.isPauseGame`. Пауза платформы имеет приоритет.
- Только `Pauser` изменяет `Time.timeScale`. Учитывай одновременно игровые окна, рекламу и скрытие вкладки.
- Скрытие вкладки останавливает игру и звук. Не рассчитывай, что платформа сделает это вместо игры.
- Музыка проходит через `AudioPlayer` и `MusicChannel`, эффекты — через существующие ограниченные наборы источников. Не обходи их прямыми вызовами `AudioSource` из игровой логики. Плавное переключение музыки уже поддерживается двумя источниками.
- Название проекта — «Mad Slime»; сохраняй его единым в настройках, материалах и консоли платформы, без чужих товарных знаков.

## Проверка перед завершением и ревью

Проверь границы задачи, понятность зависимостей, сохранность ссылок, подписки, отмену, сохранение данных и затронутые сценарии. Для интерфейса проверь оба расположения и три языка. Пользуйся имеющимися проверками; не создавай новые инструменты без просьбы.

При запросе строгого ревью проверяй весь запрошенный код, включая средства редактора. Фиксируй все найденные места, а не один пример на правило. Формат: `правило → файл:строка — нарушение`. Для статики сохраняй номер `П-61`. Одного нарушения достаточно для результата «Не соответствует». Не называй проверку полной, если часть области не проверена.
