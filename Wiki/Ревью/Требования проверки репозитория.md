# Требования проверки репозитория (сводный файл)

Единый перечень критериев, собранный из двух источников:

1. **«Чек лист _Пыточная_ шаблон.xlsx»** — официальный чек-лист ревью кода, пункты 1–55 (нумерация сохранена как в чек-листе).
2. **«Общий перечень требований для проверки репозитория.docx»** — «Перечень правил Clean Code» (авторы: Бучинский Илья, Пелип Александр) — подробные формулировки + правила, не попавшие в чек-лист (пункты 56–60).
3. **Прямое требование владельца проекта** — запрет статики (пункт 61).

**Режим проверки:** максимальная строгость. Один пункт с несоответствием = проект не сдан. По каждому пункту фиксируются **все** места нарушений в формате: `пункт → файл:строка — что нарушено`.

**Область проверки:** весь код репозитория (runtime и Editor), как рабочий лист (working tree).

---

## 1. Наименование

**П-01. Правильное использование camelCase и PascalCase.**
camelCase — параметры и локальные переменные. PascalCase — классы, структуры, интерфейсы, перечисления, методы, свойства, события, все поля кроме private/internal. private/internal поля — camelCase с префиксом `_`. Namespace — PascalCase с разделителем-точкой (`Agava.GameName.UI.Buttons`).

**П-02. Корректное наименование классов.**
PascalCase. Интерфейсы с префиксом `I`. Всегда указан модификатор доступа. По названию класса сразу понятна его задача. `Controller`/`Manager` — только по прямому назначению. Имя не содержит «And» (иначе разбить на 2). Классы обёрнуты в namespace по иерархии папок.

**П-03. Обработчики событий имеют префикс `On`** (если при вызове события вызываются несколько методов класса-слушателя).

**П-04. События:** модификатор `public`, PascalCase, окончание `-ing` если действие происходит, `-ed` если завершено (`Moving`, `Moved`).

**П-05. В названии методов нет названия класса.**

**П-06. Методы названы с глаголов** (`Get`, `Set`, `Create`, `Take`, `Attack`…), глагол применяется правильно.

**П-07. Название метода отражает суть действия.** Один метод — одно действие («КрушитьИКрамсать» → два метода). По имени не возникает вопроса «а что он делает?».

**П-08. Корректное наименование полей и переменных.**
- Всегда указан модификатор доступа.
- public/protected/protected internal/static/readonly/const поля, свойства, методы — PascalCase.
- Не использовать `protected` поля (это те же public).
- Нет безликих/индексных имён: `Фрукт1/Фрукт2/Фрукт3`, `State1/State2`, `TrueInt`, `double d`, `class A`.
- Без сокращений (кроме общепринятых).
- `var` — только когда тип очевиден из правой части; переменная названа со смыслом.

## 2. Общий перечень правил

**П-09. Нет строк, не вмещающихся в экран IDE** (порог проверки: >120 символов).

**П-10. Один файл — один класс** (вспомогательные вложенные/служебные структуры рядом с основным классом — тоже нарушение чистоты, обсуждаемо; несколько top-level классов в файле — нарушение).

**П-11. Классы обёрнуты в namespace в соответствии с иерархией папок** (`Assets/MadSlime/Scripts/Game/...` → namespace вида `MadSlime.Game...`).

**П-12. Использованы краткие формы свойств** (`public int X => _y;`), где уместно.

**П-13. Корректное использование set/get; предпочтительны авто-реализуемые свойства.**

**П-14. События из стандартной библиотеки** (`System.Action` и т.п.), помечены `event`. C# события вместо Unity (`UnityEvent` — нарушение).

**П-15. Для событий — встроенные делегаты `Action`, `Func`, `Predicate`.** Собственный делегат только при реальной потребности.

**П-16. Именование переменных типа `var` корректно** (см. П-08).

**П-17. Отсутствует оверинжиниринг.** Паттерны не должны усложнять простую задачу; нет фабрик фабрик, лишних абстракций, функционала «на будущее».

**П-18. По циклу сразу понятно, когда он закончится.** `while (true)` с неясными границами — нарушение. Для корутин, заменяющих Update и завязанных на активности объекта — `while (enabled)`.

**П-19. Дублирование отсутствует (DRY).**

**П-20. Магические числа отсутствуют** — числа в коде, смысл которых непонятен без контекста, должны быть именованными константами/полями/данными.

**П-21. Правильное использование `ref` и `out`.** `ref` — там, где меняется ссылка; `out` не нужен, если функция может вернуть значение сама.

**П-22. Нет расчётов внутри вывода текста** (вычисления выносятся в переменные до `Debug.Log`/интерполяции).

**П-23. Подписка/отписка на события** — либо в `OnEnable`/`OnDisable`, либо в `Awake`/`Start`/`OnDestroy`. Анонимные лямбды при подписке — нарушение.

**П-24. Все скрипты находятся в папке `Scripts` в соответствующих папках.**

## 3. Паттерны

### 3.1 SOLID

**П-25. SRP** — каждый класс имеет одну ответственность.
**П-26. Anti-SRP** — классы не дробятся слишком сильно, одна ответственность не размазана на несколько классов.
**П-27. OCP** — наследники добавляют функционал, не меняя поведение родителя.
**П-28. Anti-OCP** — нет чрезмерно абстрактных классов, фабрик фабрик.
**П-29. LSP** — нет наследников, меняющих логику методов базового класса.
**П-30. Anti-LSP** — наследование не используется чрезмерно и не отвергается полностью.
**П-31. ISP** — нет одного гига-интерфейса на все системы.
**П-32. Anti-ISP** — нет цепочек интерфейсов с малым числом методов, которые естественно объединить.
**П-33. DIP** — ключевые зависимости передаются через конструктор/инспектор, а не создаются внутри класса (интерфейсы). Запрещены `new`-зависимости на конкретные сервисы, `GameObject.Find`, `FindObjectOfType` как способ получения зависимостей.
**П-34. Anti-DIP** — нет классов, которым передано слишком много абстрактных зависимостей без ясной логики.

### 3.2–3.4 YAGNI / DRY / KISS

**П-35. YAGNI** — нет функционала «пригодится в будущем».
**П-36. DRY** — код не дублируется (см. П-19).
**П-37. KISS: понятный API** — по названию метода ясно, что он делает; вызов даёт ожидаемый результат.
**П-38. KISS: нет запутанных связей** между классами при вызовах.

### 3.5–3.7 FSM / Entry Point / Factory

**П-39. FSM** — при смене состояний объекта применяется паттерн конечного автомата.
**П-40. У игры есть конкретная точка входа** (можно точно определить, откуда начинается).
**П-41. Все механики имеют собственную точку входа.**
**П-42. Factory** — при создании экземпляра из шаблона применяется паттерн Factory.
**П-43. Factory** — при шаблонном создании настраиваемых объектов применяется Factory.

## 4. Замечания общего характера

**П-44. В коде отсутствует `Debug.Log`** (любые Debug-выводы: `Log`, `LogWarning`, `LogError`, `Assert` — фиксировать все).

**П-45. Прочие замечания вне конкретных пунктов** (свободная форма).

**П-46. Потенциальный NullRef** — разыменование без проверки (компоненты без `TryGetComponent`/null-check, события без `?.Invoke`, доступ до `Awake` и т.п.).

**П-47. Перебор значения переменной через `if/else` вместо `switch`** (3+ веток по одной переменной).

**П-48. Неиспользуемые поля.**
**П-49. Неиспользуемые свойства.**
**П-50. Неиспользуемые события.**
**П-51. Неиспользуемые методы** (учитывать: Unity-магия, сериализованные поля/инспектор, интерфейсные реализации — не «неиспользуемые»).

**П-52. Методы `Try*` без возвращаемого типа `bool`.**

**П-53. Создание нового объекта задержки каждый кадр/вызов:** `new WaitForSeconds(...)` и прочие `YieldInstruction` должны кешироваться в поля.

**П-54. Неиспользуемые `using`.**

**П-55. Оптимальное использование `if/else`** (лишние вложенности, дублирующиеся условия, `if (x == true)` и т.п.).

## 5. Дополнительно из docx (не покрыто чек-листом)

**П-56. Порядок расположения элементов класса:**
static/readonly/const поля → поля с атрибутами → поля → делегаты → конструктор → события → свойства → встроенные Unity-методы → методы → обработчики событий. Внутри групп — по модификаторам: `public`, `internal`, `protected internal`, `protected`, `private`.

**П-57. Пробелы и отступы:** условные операторы и циклы отделяются отступами спереди и сзади; не писать всё в одну строку; открывающая и закрывающая фигурные скобки — на отдельных строках (Allman).

**П-58. Тело циклов и условных операторов всегда заключено в фигурные скобки.**

**П-59. Не использовать сокращения** в именах (кроме общепринятых).

**П-60. Нет повторения имени класса внутри класса** — имена полей и методов не должны содержать имя класса, в котором находятся.

## 6. Обязательные требования проекта

**П-61. В проекте запрещена статика.**

Запрещены статические поля (включая `static readonly`), конструкторы, методы, свойства, события и классы. Правило действует для runtime и Editor-кода независимо от модификатора доступа.

Единственное исключение — утилиты без состояния по типу `ArgumentGuard`: допускаются статический класс и его статические методы, которые работают только с переданными аргументами и не хранят состояние. Статические поля и конструкторы запрещены и в таких утилитах. Игровые системы и сервисы нельзя объявлять утилитами для обхода запрета.

Оптимизация, кеширование, удобство вызова, требования Editor API и формулировка «если критично» не являются исключениями. При конфликте с другими правилами проекта, включая правила именования и порядка членов класса, этот запрет имеет приоритет.

Любое нарушение — результат «Не соответствует» и проект не сдан. При ревью фиксируются все нарушения в формате `П-61 → файл:строка — что нарушено`.
